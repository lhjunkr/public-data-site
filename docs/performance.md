# 성능 측정

매칭 검색(`POST /api/v1/policies/match`)의 응답 시간을 구간별로 재고, 개선 전후를 같은 방법으로 비교한다. 개선 결정은 D-027.

## 측정 방법

| 항목 | 내용 |
|---|---|
| 도구 | `scripts/measure.sh <URL> [본문.json] [횟수=30]` — 같은 요청을 30번 보내 구간별 p50(중앙값) · p95를 낸다. 요청마다 새로 연결한다(처음 방문한 사용자 기준) |
| 구간 | DNS → TCP(연결, ≈ 왕복 1번) → TLS(암호화 연결) → SERVER(요청 → 첫 바이트 = 서버 처리 + 왕복 1번) → TRANSFER(첫 바이트 → 마지막 바이트) |
| 검색 조건 | `scripts/match-25-seoul.json` — 25세 · 서울, 소득 · 취업 상태 없음 |
| 응답 분해 | `scripts/response-size.py 응답.json` — 필드별 바이트 (1KB = 1,000바이트) |
| 맥 | 맥북 → 휴대폰 핫스팟(LTE) → `https://chajaga.com`. 사용자가 겪는 전체 시간 |
| 서버 안 | 앱 서버에서 `http://localhost:8080`. 인터넷 · Caddy · TLS가 빠져 **앱 + DB만** 남는다 |
| 조건 점검 | 측정할 때마다 맥 `/health`의 TCP p50이 61 ~ 65ms 근처인지 확인한다. 크게 다르면 그날 조건을 기록한다 |
| 서버 | 앱 · DB 각각 오라클 `VM.Standard.E2.1.Micro`(1/8 OCPU · 1GB), 도쿄 |

### Before에서 알게 된 것

1. **사용자 시간의 약 절반(557ms)이 앱 + DB 안에서 쓰인다.** 같은 조건의 `/health`는 서버 안에서 4.2ms다. SQL · 데이터 읽기 · JSON 만들기 중 어디인지는 아직 모른다.
2. **전송 280ms(24%)는 인터넷 구간에서만 생긴다.** 크기를 줄이면 이 몫이 함께 줄 것으로 본다(추론).
3. **응답의 54%가 `supportContent`(지원 내용 긴 글)다.** 목록에서 빼면 약 164KB가 된다(계산).
4. **11/2 가설 수정:** "응답 크기(357KB)가 병목"이라고 봤으나, 크기가 직접 만드는 전송은 24%이고 앱 + DB가 47%다.
5. 서버 안에서도 p95가 p50보다 크게 길다(`/health` 4.2 → 68.4ms, 매칭 557 → 779ms). 원인은 확인하지 않았다(1/8 OCPU의 순간 성능 변동, GC 후보).
6. 코드에서 본 것(효과 미측정): 매칭 SQL이 `extra_qualification`(TEXT)을 통째로 읽지만 응답에는 `needsCheck` 참/거짓만 쓴다. 요청 1번에 쿼리가 3개(시도 확인 · 매칭 · 분류 칩) 돈다.

### 알려진 한계

- 30회라 p95는 사실상 두 번째로 느린 값이다. 꼬리 지연을 말하기에는 표본이 얇다.
- 맥 측정은 핫스팟(LTE)이라 시간 · 장소에 따라 흔들린다 → 조건 점검으로 관리한다.
- 맥 매칭(11:36)과 서버 안(11:56)은 20분 차이가 난다.
- 맥 매칭은 정렬 버그를 고치기 전 스크립트로 쟀다. 버그는 0.1ms 미만 값의 순서만 틀리게 했고, 이 측정의 모든 구간은 그보다 커서 영향이 없다.
- 요청마다 새로 연결하므로, 연결을 재사용하는 브라우저의 두 번째 검색보다 약 149ms 느린 쪽의 값이다.

## 원인 분석 1 — 매칭 SQL (2026-11-10)

`scripts/explain-match.sql`은 앱의 `MATCH_SQL`과 같은 SQL이다(파라미터만 MySQL 변수로 바꿈). DB 서버의 MySQL 안에서 실행했다.

### SQL 시간

| 측정 | 값 |
|---|---|
| `EXPLAIN ANALYZE` 전체 (5회) | 625 · 621 · 895 · 615 · 617ms |
| 실제 `SELECT` + 결과 482행 받기 (DB 서버 안, 5회) | 0.52 · 0.58 · 0.59 · 0.59 · 0.53초 → **중앙값 0.58초** |
| 비교: 앱 + DB (서버 안 매칭 SERVER p50) | 0.557초 |

→ **앱 + DB 시간의 대부분이 매칭 SQL이다.** DB 서버의 `mysql` 클라이언트가 MySQL과 같은 1/8 CPU를 나눠 쓰고 시간 단위가 0.01초라, 정확한 비율은 내지 않는다.

### 실행 계획 (`EXPLAIN ANALYZE`, 안쪽부터 실행 순서)

| 순서 | 단계 | 행 | 누적 ms |
|---|---|---|---|
| 1 | `policy` 전체 읽기 (Table scan) | 3,982 | 9 |
| 2 | 활성 · 나이 · 마감일로 거름 | 2,308 (MySQL 예상 41) | 12 |
| 3 | `region`에서 시도 `11`인 지역 코드 | 25 | 0.2 |
| 4 | 조건 없는 조인 = 정책 × 지역 코드 짝을 모두 만듦 | **57,700** | 219 |
| 5 | 짝마다 `policy_region` 기본 키로 "이 정책에 이 지역이 있나" 확인 (`loops=57700`) | 11,820 | **590** |
| 6 | 정책별 중복 제거 (weedout) | 482 | 595 |
| 7 | 분류 칩 확인 (`loops=482`) | 482 | 618 |
| 8 | 조회수 순 정렬 | 482 | 625 |

- **4 ~ 5단계가 약 580ms(약 93%)다.** MySQL이 지역 `EXISTS`를 semijoin(짝이 있는 것만 남기는 조인)으로 바꾸고, "짝을 다 만든 뒤 중복을 거르는(weedout)" 방식을 골랐다.
- 이 방식을 고른 이유로 보이는 것: 2단계 결과를 41건으로 예상했다(실제 2,308건, 약 56배). 41건이면 41 × 25 ≈ 1,000번 확인이라 싸 보인다(추정).
- 나이 · 마감일 범위 조건은 표 전체를 읽고도 12ms(약 2%)다. `idx_policy_age`는 쓰이지 않았다.

### DB → 앱 데이터 (결과 482행, 칸별)

| 칸 | KB | 응답(JSON)에서 |
|---|---|---|
| `support_content` | 183.7 | 그대로 나감 |
| `extra_qualification` | **56.3** | 나가지 않음 — `needsCheck` 참/거짓에만 쓴다 |
| `ref_url` | 19.8 | 그대로 나감 |
| `title` | 19.0 | 그대로 나감 |
| 나머지 8칸 | 37.9 | `earn_etc_cn`(4.8)은 소득 조건이 문장인 정책만 나감 |
| **합계** | **316.7** | |

`extra_qualification`은 DB → 앱 데이터의 18%지만, 같은 사설망 안의 57KB라 시간 몫은 작다고 본다(추정).

### D-009 전제 판정

D-009 "기술적 차별점은 다중 범위 인덱스 최적화" → **겨냥한 곳이 틀렸다.** 범위 조건(나이 · 마감일)은 약 2%이고, 병목은 지역 `EXISTS`의 실행 방식(약 93%)이다. "SQL을 고쳐야 한다"는 방향은 맞지만, 고칠 곳은 범위 인덱스가 아니라 지역 확인이다. D-009는 11/25에 측정 결과로 고쳐 쓴다.

### 측정하며 알게 된 것

- DB 서버 컨테이너 안의 `mysql` 클라이언트는 기본 글자 체계가 `latin1`이라 한글을 `?`로 바꿔 보여 준다. 한글이 섞인 결과를 보거나 잴 때는 `--default-character-set=utf8mb4`를 붙인다. 처음 잰 칸별 크기는 한글 칸이 2 ~ 3배 작게 나와 버렸다.
