# 설계 결정 기록

결정 하나당 한 항목. 뒤집힌 결정은 지우지 않고 "→ D-0XX로 변경"을 덧붙인다.
조인 테이블 채택의 상세 근거는 [ADR-001](adr/ADR-001.md) 참고.

| 번호 | 결정 | 근거                                                                                                                                                                                                                             |
|---|---|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| D-001 | 이 서비스는 자격을 "판정"하지 않고 후보를 "좁히는 필터"다 | 자격 조건 일부가 자유 서술이라 기계가 확정할 수 없다                                                                                                                                                                                                 |
| D-002 | 매칭 결과는 3가지 상태: 충족 / 미충족 / 판단불가 | 소득 조건의 9%가 숫자 없이 글로만 적혀 있다                                                                                                                                                                                                     |
| D-003 | 자유 서술 필드는 해석하지 않는다. `addAplyQlfcCndCn`이 비어 있지 않으면 "확인 필요" 표시 | 자연어 해석은 오판 위험이 크고 범위 밖이다                                                                                                                                                                                                       |
| D-004 | 전량 정규화 대신 30건 큐레이션 → D-014로 변경 | 9월 일정 안에 정확도를 확보하기 위함 |

| D-007 | 승인된 정책(`plcyAprvSttsCd=0044002`)만 저장 | 미승인 정책은 노출 대상이 아니다                                                                                                                                                                                                             |

| D-010 | 성능 실험은 실제 데이터로 한다 | 가짜 데이터는 분포가 달라 결과를 믿을 수 없다                                                                                                                                                                                                     |
| D-011 | 대상 분류 범위는 설정 파일로 관리 | 범위를 바꿀 때 코드를 고치지 않기 위함                                                                                                                                                                                                         |
| D-012 | 취업 상태 축은 9/25 보류. 현재 매칭은 3축(나이 · 시도 · 소득). 수집한 값은 `policy_job` 테이블에 그대로 둔다. 코드 뜻을 명세로 확인하면 구현한다 → D-021로 변경 | 취업 상태 코드(`0013010` 등)의 뜻이 확인된 것이 아니라 빈도로 추측한 것이다. 추측으로 조건을 걸면 자격 없는 사람에게 "충족"이 뜨거나 자격 있는 사람의 정책이 결과에서 빠진다. 조건을 걸지 않으면 결과가 넓어질 뿐 틀린 안내는 없다(D-001)                                                                               |
| D-013 | 배포는 PR이 `main`에 머지되고 CI가 통과했을 때만 자동으로 실행한다. 이미지 태그는 커밋 SHA를 쓴다(`lhjunkr/policy-match:<SHA>`). 문제가 생기면 서버에서 `deploy.sh <이전 SHA>`로 이전 이미지로 되돌리고, `main`의 문제 커밋도 되돌린다. 서버가 2대 이상이 되거나 DB 변경이 잦아지면 다시 검토한다 | `feature` 브랜치나 PR 단계에서 배포하면 검토와 테스트가 끝나지 않은 코드가 공개 URL에 올라간다. `latest`는 같은 이름이 매번 다른 내용을 가리켜, 서버가 어느 커밋을 돌리는지 알 수 없고 되돌릴 대상도 없다. SHA 태그는 커밋마다 하나씩 남으므로 다시 빌드하지 않고 태그만 바꿔 되돌릴 수 있다. 단, 되돌아가는 것은 앱뿐이고 Flyway가 적용한 DB 변경은 그대로 남는다 10/30 실제 롤백에서 확인: V6를 적용한 뒤 옛 앱(`7589c52`)으로 되돌려도 떴다 — Flyway는 옛 앱이 모르는 새 마이그레이션을 무시한다(열·표 추가처럼 기존 것을 지우지 않는 변경에 한함) |
| D-014 | 매칭 대상을 30건 큐레이션 대신 규칙으로 고른다. 규칙은 승인된 정책(D-007) 중 중분류 3개(취약계층 및 금융지원 · 주택 및 거주지 · 전월세 및 주거급여 지원)에 속하고 가장 최근 수집에서 확인된 정책이며, 건수 상한은 두지 않는다. 마감 여부는 정규화에서 보지 않고 매칭할 때만 거른다(D-008 유지). 규칙에서 빠진 정책은 지우지 않고 `active = FALSE`로 표시해 매칭에서 제외하고, 다시 규칙에 들면 `TRUE`로 되돌린다. 비활성 처리는 수집이 끝까지 성공했을 때만 실행한다 → 수집 기준은 D-017, 분류 범위는 D-018로 변경 | 기존 30건은 사람이 고른 것이 아니라 정책번호 순 앞 30건이었고 마감일을 보지 않아 17건이 만료, 25세·서울 결과가 1건이었다. 같은 분류 안에 신청 가능한 정책이 387건(9/25, 상시 329 + 진행중 58) 있다. 마감 필터를 정규화에도 넣으면 다음 날 마감되는 정책 때문에 매칭 단계 필터가 어차피 필요해 같은 규칙이 두 곳에 생긴다. upsert는 행을 지우지 않으므로 승인 취소·분류 변경·API 삭제 정책이 계속 노출되고, 삭제하면 연결 표를 먼저 지워야 하며 다시 나타날 때 id가 바뀐다. 대가: 수백 건이라 수동 보정을 할 수 없어 판단불가와 "확인 필요"가 늘어난다. 수집이 중간에 끊기면 정상 정책이 대량으로 비활성될 수 있어 안전장치가 필요하다 |
| D-015 | 나이는 `age_limit_yn` 표시값을 보지 않고 최소·최대 나이 값으로만 판단한다. 0 또는 값 없음은 그쪽 경계가 없다는 뜻이다(0/0 = 제한 없음, 18/0 = 18세 이상, 0/39 = 39세 이하). 최소 > 최대로 뒤집힌 값은 판단할 수 없으므로 결과에 포함한다(D-001) | 9/25에 30건으로 세운 "`Y` = 제한 없음"은 전체 742건에서 성립하지 않았다. `Y`이면서 나이 범위가 있는 153건 중 37건은 원문에 같은 최대 나이가 적혀 있다(예: 19~30 → "만19세 ~ 30세 미만"). `N`인데 0/0인 16건은 원문에 나이 표기가 1건뿐이라 제한 없음으로 보이는데, 예전 규칙에서는 0세가 아니면 결과에 나오지 않았다. 최소 > 최대였던 4건은 모두 18/0이고 원문이 "만 18세가 되어 보호가 종료된" 같은 18세 이상 조건이었다 (`docs/quality-check.md`) |
| D-016 | 소득 금액은 만원 단위로 저장한다. 10만 이상인 값은 원 단위로 보고 만원으로 바꾼다(올림). 금액비교(`0043002`)는 상한을 기준으로 본다: 상한이 없으면 판단불가, 상한을 넘으면 미충족, 상한 이하인데 하한이 있으면 판단불가, 하한이 없으면 충족 | 금액비교 40건 중 38건은 534~20,000이고 원문도 "연소득 5,000만원"처럼 만원 단위였다. 1건만 43,056,240으로 원 단위였다. 만원 단위로 10만(10억 원)을 넘는 청년 소득 기준도, 원 단위로 10만 원 미만인 연소득 기준도 없으므로 10만이 안전한 경계다. 하한이 있는 6건 중 원문으로 확인된 건은 하한이 아니라 다른 대상의 기준이었다(예: 취업준비생 4,500만원). 하한으로 미충족을 내면 틀릴 수 있지만, 상한을 넘으면 어느 해석으로도 미충족이다. 상한이 0인 1건은 예전에 모두에게 "미충족"으로 표시됐다 |
| D-017 | 수집 실행마다 결과를 `collect_run` 표에 남기고(RUNNING → SUCCESS/FAILED), 정규화는 **마지막으로 성공한 수집**이 시작된 뒤에 확인된 정책만 고른다(D-014의 "가장 최근 수집"을 대체). 수집은 끝까지 읽고 API 전체 건수의 95% 이상을 받아야 성공이다. 성공한 수집이 없으면 정규화하지 않는다. API의 400 응답은 다시 시도한다 | 10/30 첫 수집이 9페이지에서 400(e002)으로 실패했는데, "가장 최근 수집" 기준 정규화가 앞 800건만 보고 정상 정책 30건을 비활성했다. 같은 요청을 다시 보내자 200이었으므로 이 API의 400은 일시 오류일 수 있다. 성공 수집 뒤의 실패한 수집에서 갱신된 정책도 존재가 확인된 것이므로 "이후(≥)"로 비교해 함께 고른다. 95%는 수집 도중 정책이 몇 건 삭제되는 정도(O-4)를 허용하기 위한 여유다 |
| D-018 | 승인된 정책은 분류와 상관없이 모두 정규화하고, 화면 분류는 묶음표(`application.yml`의 `category.tabs`)로 정한다. 탭 5개(주거 · 금융·복지 · 교육 · 참여 · 일자리) 아래 칩을 최대 3개 두고, 원본 중분류 하나는 칩 하나에만 속한다. 정책은 자기 중분류를 따라 여러 칩에 속할 수 있고 `policy_category`에 칩 코드(`탭.칩`)로 저장한다. 이름 비교는 공백과 가운뎃점을 무시한다. 일자리 탭은 취업 상태 조건(D-012) 전까지 닫아 두며, 닫힌 탭의 칩만 가진 정책과 분류가 없는 정책은 결과에 나오지 않는다 | 3,763건 측정(10/30): 두 세대 대분류를 합치면 일자리 1,449 · 금융·복지·문화 897 · 교육 555 · 참여·기반 527 · 주거 385로 원래 5개가 가장 큰 덩어리다. 원본 대분류는 이름이 두 세대로 섞이고 콤마 값끼리 짝을 알 수 없어(예: `일자리,교육` + `취업,미래역량강화`) 중분류를 기준으로 묶었다. 중분류도 두 쌍은 이름이 바뀌었다(`문화활동` → `문화활동 및 생활지원`, `온라인교육` → `온·오프라인교육`). 사용자가 복잡하다고 느끼지 않도록 칩을 탭마다 3개 이하로 하고, 100건 미만 덩어리는 가까운 칩에 합쳐 "기타"를 없앴다(휴대폰 한 줄). 두 세대가 다른 탭에 둔 중분류(권익보호)는 새 세대를 따랐다. 일자리의 핵심 조건은 취업 상태라 조건 없이 열면 결과가 지나치게 넓다 |
| D-019 | 정규화는 정책 단위로 실패를 격리한다. DB에 넣다가 실패한 정책은 건너뛰고 로그와 `failed` 수로 남기며, 결과에서 빠진다(비활성). 실패가 10건 또는 후보의 1%를 넘으면 구조 문제로 보고 전체를 되돌린다. 칸 크기는 전체 데이터의 실측 최대로 정한다(URL 2,048자, 분류 이름 200자) | 10/30 첫 전체 정규화(3,763건)가 `ref_url` 1건(542자 > 칸 500자) 때문에 47초 만에 전체 실패했고, 새 버전은 분류 연결 표가 비어 있어 검색 결과가 0건이 됐다. 서버 로그를 먼저 저장한 뒤 이전 버전으로 롤백해 복구했다(D-013). 742건에서 안전했던 칸 크기가 3,763건에서 깨졌다 — 데이터가 늘면 극단값도 늘어난다. 실패 한 건 때문에 나머지 3,762건을 버리는 것은 과하지만, 많이 실패하는데도 진행하면 잘못된 상태가 공개된다 |
| D-020 | 수집 → 정규화를 매일 한국 시간 04:10에 자동으로 돌린다(`@Scheduled`, 시간대 `Asia/Seoul` 고정). 정규화는 수집이 성공했을 때만 돈다. 관리용 엔드포인트와 자동 실행은 모두 한 입구(`PolicyBatch`)를 거치고 한 번에 하나만 돈다. 실행 중에 들어온 요청은 기다리지 않고 409로 거절한다. 자동 실행이 실패하면 재시도하지 않고 로그만 남긴다. 앱이 2대 이상이 되면 앱 안 잠금을 DB 잠금으로 바꾼다 | 수동 실행은 사람이 잊으면 데이터가 낡는다. 10/30에는 수집이 실패한 뒤 정규화를 돌리는 실수가 있었다 — 순서를 코드로 고정한다. 정규화 한 번(약 70초)이 MySQL 잠금 대기 한도(기본 50초)보다 길어 둘이 겹치면 뒤의 것이 실패하고, 수집이 겹치면 외부 API를 두 배로 부른다. 앱이 한 대라 앱 안 잠금으로 충분하다. 재시도는 API 장애가 몇 분 안에 풀린다는 근거가 없어 두지 않았다. 실패해도 화면은 마지막 성공 데이터를 보여 준다(D-017). 04:10은 사용자가 적은 새벽이고, 정각을 피했다 |
| D-021 | 취업 상태를 매칭 조건에 넣는다. 사용자는 공식 코드표(`jobCd`)의 9개 상태 중 하나를 고르거나 고르지 않는다(선택 사항). 고르면 정책 코드에 제한없음(`0013010`)이나 고른 코드가 있는 정책만 내고, 고르지 않으면 거르지 않는다. 선택지는 공식 값이라 설정 파일이 아니라 코드(`JobStatus`)에 둔다. 일자리 탭을 연다 | 10/30 온통청년 공식 코드표(`API코드정보.xlsx`)로 코드 뜻을 확인했다. 9/7의 빈도 추정(`0013010` = 제한없음)이 맞았다. 실측(활성 3,763건): 제한없음 2,795건, 코드가 없는 정책 0건, 제한없음과 다른 코드가 함께 붙은 정책 0건이라 따로 다룰 경우가 없다. 여러 개를 고르게 하지 않은 이유: 선택지 9개를 체크박스로 늘어놓으면 화면이 복잡해진다. 여러 상태에 걸친 사용자는 고르지 않고 전체를 보면 된다. 코드 없는 정책이 생기면 취업 상태를 고른 사용자에게서 빠지므로 품질 측정 [10]으로 감시한다 |
