# 9월 회고 (9/1 ~ 10/4)

개발 프로젝트를 처음 해 보는 상태에서 시작해, 공개 URL에서 동작하는 서비스까지 만든 5주의 기록이다.
잘한 것을 늘어놓기보다 틀렸던 것과 그 원인을 남기는 데 목적이 있다.

## 1. 결과

| 항목 | 값 |
|---|---|
| 공개 URL | http://161.33.139.178:8080/ (9/15 최초 공개, 10/1 매칭 기능 반영) |
| 기능 | 나이 · 시도 · 소득 3축 매칭, 소득 조건 3가지 상태(충족 / 미충족 / 판단불가) |
| 데이터 | 원본 3,106건 수집(10/1 기준) → 30건 정규화 |
| 테스트 | 18개 (경계값 · 입력 검증 · API 통합), CI에서 자동 실행 |
| 기록 | 설계 결정 D-001 ~ D-012, ADR 1건 |

## 2. 계획과 실제

| 단계 | 계획 | 실제 |
|---|---|---|
| 환경 준비 · SQL · 설계 | 9/1 ~ 9/8 | 계획대로 |
| Walking Skeleton (공개 URL) | 9/9 ~ 9/15 | **9/15 공개** — 계획대로 |
| 수집 · 정규화 | 9/16 ~ 9/18 | 사흘간 손대지 못함 → 9/21 하루에 완료 |

| 화면 · 재배포 | 9/28 ~ 9/29 | 10/1 완료 — 2일 지연 (화면은 Claude Code로 생성 후 검수) |
| 문서 · 리포 공개 | 9/30 | 10/4 완료 — 4일 지연 |

반드시 지키기로 한 기한 두 개 중 **9/15 공개 URL은 지켰고, 9/23 매칭 엔진 푸시는 9/25에 끝냈다.**

## 3. 잘된 것

### 3-1. 끝까지 관통하는 최소 버전을 먼저 만들었다

9/15에 `/health`와 정적 화면만 있는 상태로 공개 URL을 먼저 열었다.
방화벽 설정, 1GB 메모리 제약, 맥(ARM)과 서버(x86)의 차이 같은 배포 문제를 기능이 거의 없을 때 겪었기 때문에, 원인을 배포 쪽으로만 좁힐 수 있었다.
이후 기능은 이미 돌아가는 구조 위에 얹기만 하면 됐다.

### 3-2. 코드를 쓰기 전에 데이터를 집계했다

계획서에는 "금융 · 주거 30건"이라고만 적혀 있었다.
대분류로 거르는 코드를 쓰기 전에 수집한 원본을 `GROUP BY`로 집계해 보니, 같은 중분류 "취약계층 및 금융지원"이 대분류 `복지문화`(171건)와 `금융･복지･문화`(132건)에 나뉘어 있었다.
대분류로 걸렀다면 어느 쪽을 골라도 절반을 놓쳤을 것이다. 그래서 중분류 기준으로 바꿨다.

### 3-3. SQL을 손으로 먼저 쓰고 나서 API로 옮겼다

매칭 SQL을 DB에서 한 층씩 쌓으며 결과 건수를 예상과 맞춰 봤다. 이 과정에서 두 가지를 발견했다.

- `JOIN`만 쓰면 전국 대상 정책 1건이 서울 25개 구와 짝지어져 25줄로 나온다 → `EXISTS`로 바꿨다.
- 문자열 `"NULL"`은 오류 없이 0으로 바뀌어 "충족"이 나온다 → 입력 검증을 SQL 앞에 뒀다.

API부터 만들었다면 둘 다 화면의 틀린 결과로만 보였을 것이고, 원인을 찾는 데 훨씬 오래 걸렸을 것이다.

### 3-4. 모르는 것을 추측으로 메우지 않았다

자격 조건 일부는 자유 서술이라 기계가 확정할 수 없다. 그래서 서비스를 "판정"이 아니라 "후보를 좁히는 필터"로 정했고(D-001), 비교할 수 없는 소득 조건은 "판단불가"로 남겼다(D-002).
취업 상태 코드는 뜻을 확인하지 못해 조건을 걸지 않았다(D-012).
조건을 걸지 않으면 결과가 넓어질 뿐이지만, 추측으로 걸면 틀린 안내가 나온다.

## 4. 문제였던 것

### 4-1. 여유가 0일인 계획은 하루만 비어도 밀린다

9/16 ~ 9/18 사흘 동안 작업을 하지 못했다.
9/21 하루에 사흘치를 처리해 범위(30건)는 지켰지만, 그 여파로 매칭 엔진이 추석 연휴(9/25)로 넘어갔고 전체 마감이 4일 밀렸다.
계획을 세울 때 "밀리면 날짜를 미루지 않고 범위를 자른다"고 정해 두었으나, 실제로는 범위를 지키고 날짜를 미뤘다.

### 4-2. 일부만 보고 내린 결론이 세 번 틀렸다

| 처음 적은 것 | 실제 | 어떻게 알았나 |
|---|---|---|
| `age_limit_yn`이 `N`이면 나이 무관 | 반대였다. `Y`가 제한 없음 | 나이가 0/0인 정책 8건이 전부 `Y` |
| 콤마로 이어진 다중값은 `jobCd`에만 있다 | 대분류에도 있었다 | 표본 100건이 아니라 전량을 집계 |
| 선정한 30건은 모두 쓸 수 있다 | 로컬 기준 17건이 이미 마감 | 매칭 결과가 1건뿐이라 확인 |

세 번 모두 확인하지 않은 것을 사실처럼 적은 것이 원인이다.
지금은 확인하지 못한 것에는 "추정"이라고 적고, 추정에는 조건을 걸지 않는다.

### 4-3. 기록이 실제보다 늦었다

- 설계 결정은 10/3까지 리포에 없었다. 결정한 날이 아니라 한참 뒤에 한꺼번에 옮겼다.
- ERD는 두 번째 마이그레이션(소득 열, `policy_job` 표)을 아직 반영하지 못했다.
- 공개 URL은 9/15 버전인 채로 10/1까지 남아 있었다. 매칭 API는 9/25에 완성됐지만 배포가 수동이라 미뤄졌다.

### 4-4. 명령을 줄바꿈으로만 이어 붙여 장애를 냈다

9/15에 DB 비밀번호를 바꾸면서 명령 여러 줄을 순서대로 붙여 넣었다.
비밀번호를 바꾸는 `ALTER`가 실패했는데도 다음 줄이 그대로 실행되어 `.env`만 새 값으로 바뀌었고, 앱이 DB에 접속하지 못했다.
절차를 `&&`로 묶고 단계마다 접속을 확인하도록 다시 썼다.

### 4-5. 같은 실수를 반복했다

브랜치 이름 오타, 자리표시자(`<...>`)를 지우지 않고 실행, 다른 터미널 탭에 명령 입력이 각각 두세 번씩 있었다.
실행 전에 한 줄로 확인하는 습관으로 줄였다.

| 실수 | 확인 방법 |
|---|---|
| 브랜치 이름 오타 | 만든 직후 `git branch --show-current` |
| 자리표시자 미삭제 | 값의 길이로 확인 |
| 엉뚱한 곳에서 실행 | 치기 전에 프롬프트 마지막 줄 확인 |

## 5. 배운 것

| 주제 | 한 문장 |
|---|---|
| 조인 테이블 | 다중값을 콤마 문자열로 두면 정확히 일치하는 검색, 집계, 무결성 검사를 모두 잃는다 |
| 멱등성 | 근거는 코드가 아니라 스키마(UNIQUE 제약)에 있다. 연결 표는 지우고 다시 넣어야 줄어든 값도 반영된다 |
| 외부 API | 인증 실패를 `200` + HTML로 주는 API가 있다. 타임아웃을 걸고, 5xx는 재시도하고 4xx는 바로 포기한다 |
| `EXISTS` | "하나라도 있는가"만 보므로 `JOIN`처럼 줄이 불어나지 않는다 |
| 입력 검증 | 잘못된 값이 SQL까지 가면 오류 없이 틀린 답이 나올 수 있다 |
| 배포 | 1GB 서버에서는 빌드할 수 없어 로컬에서 이미지를 만들고 레지스트리를 거친다 |
| 비밀값 | compose에는 변수 이름만, 실제 값은 서버의 `.env`에만 둔다 |

## 6. 아직 해결하지 못한 것

- 매칭 대상이 직접 고른 30건이고, 선정 기준이 마감일을 보지 않는다
- 취업 상태 조건 미반영 (D-012)
- 소득 금액의 단위(만원)가 추정이다
- `region` 표에 시군구 이름이 없다
- ERD가 최신 스키마와 다르다
- 배포와 수집이 수동이다
- 주소가 IP + HTTP다
