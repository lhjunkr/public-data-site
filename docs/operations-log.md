# 운영 기록

운영 서버에서 직접 확인한 결과와 수치를 날짜순으로 남긴다. 설계 결정과 그 근거는 [`decisions.md`](decisions.md), 성능 측정은 [`performance.md`](performance.md), 데이터 품질과 사건은 [`quality-check.md`](quality-check.md)에 있다.

- 날짜는 실제로 확인한 날이다. 괄호 안의 날짜는 12월 계획표에서 그 작업이 잡혀 있던 날이다.
- 비밀값, 서버 주소, 백업 암호문 이름처럼 공격에 쓰일 수 있는 값은 적지 않는다.

## 11/26 — K-Startup 수집기 로컬 실행 (12/9)

맥 로컬(MySQL 8.4)에서 실제 API로 `POST /api/v1/admin/collect?source=kstartup`을 두 번 불렀다.

| 확인 | 결과 |
|---|---|
| 테스트 | 161개 통과 (139 → +22), 20초 |
| 1회차 | `totCount`(= `matchCount`, 모집 중) 181 · 2페이지 · 받은 181 · `policy_raw` kstartup 181행 → 성공 (100%, 기준 95%) |
| 2회차 | 같은 181 · 181행 그대로 → 중복 없음 (`(source, policy_no)` upsert) |
| 호출 수 | 1회에 2번 (100건씩). 일일 한도 10,000 |
| 추이 | 모집 중 공고 11/25 175건 → 11/26 181건 |

- 운영 적재는 12/16(서버 `.env`에 `DATA_GO_KR_KEY` 추가 · 매일 갱신 편입).

## 11/25 — 하루 비활성 분포 (12/8 대량 변경 감지의 상한 근거)

지금 비활성인 온통청년 정책 58건을 마지막으로 바뀐 날(= 비활성된 날)로 묶었다. 다시 살아난 행은 셀 수 없으므로 실제보다 작게 나올 수 있다(하한값).

| 날짜 | 11/3 | 11/4 | 11/5 | 11/7 | 11/11 | 11/13 | 11/14 | 11/17 | 11/18 | 11/20 | 11/24 | 합계 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 비활성 | 1 | 1 | 4 | 3 | 1 | 1 | 1 | 2 | 11 | **26** | 7 | 58 |

- 하루 최대 26건(11/20)이다. 활성 3,994건의 0.7%다.
- 상한 `max(50, 활성의 10%)` = 399건은 최대의 15배이고, 바닥 50건도 최대의 약 2배다 → 평소 변동으로는 멈추지 않는다 ([D-019](decisions.md) "12/8 추가").

## 11/25 — V10 출처(source) 구조 배포 (12/7)

[D-029](decisions.md)의 첫 단계다. `policy` · `policy_raw` · `collect_run`에 `source`(지금은 `youth`)를 두고, 유니크 키를 `(source, policy_no)`로 바꿨다. 수집 · 정규화 · 비활성은 출처별로 한다. 테스트는 117개에서 125개가 됐다.

## 11/24 ~ 25 — 오프사이트 백업 · 복원 리허설 (12/4)

결정과 근거는 [D-026](decisions.md) "12/4 추가"에 있다.

| 확인 | 결과 |
|---|---|
| 수동 백업 (11/24 22:01) | 백업 완료 · 외부 사본 완료 (3.6MB). 백업 앞뒤로 표 건수 같음 |
| 크기 | 원본 3,763,139바이트 = 외부 사본(복호화 기준) 3,763,139 · 저장소의 암호문 3,764,099 (+960 = 헤더 32 + 64KiB 블록 58개 × 16) |
| 복원 리허설 (맥) | 오라클 서버 두 대를 쓰지 않고 외부 저장소 + 비밀번호 관리자의 값만으로 내려받음 → MD5가 운영 파일과 일치 → 빈 MySQL에 복원 → 표 10개 건수 모두 일치 (`policy` 4,052 · `policy_region` 212,246) |
| 첫 자동 실행 (11/25 04:40) | 백업 완료 · 외부 사본 완료. 사람 없이 cron으로도 외부 사본까지 성공 |
| 처리방침 | `/privacy.html`에 외부 저장소(미국) 국외 보관 고지 반영 |

리허설에서 찾은 빈틈은 두 가지다.
1. **백업 암호가 서버 밖에 없었다.** 서버를 잃었다면 외부 사본을 영원히 풀 수 없었다. 지금은 비밀번호 관리자에 있다.
2. **암호가 틀려도 오류가 나지 않는다.** 빈 목록만 나온다. 그래서 복원 전에 암호로 만든 폴더 이름이 저장소의 폴더 이름과 같은지 먼저 확인한다.
